# Phase 3 results, 2026-11-18

Phase 3 tested named sections of the skills, not whole files. Each test family
plants a situation where one skill rule should change what the agent does, and
runs three arms:

- `full`: the deployed skills;
- `minus-skill`: the whole body of the skill under test removed;
- `minus-candidates`: only the candidate sections for that rule removed.

The `minus-skill` arm shows whether the scenario can detect the skill at all.
The `minus-candidates` arm shows whether the candidate sections are what carry
the effect.

Skills were pinned at catalog commit `a0c0d4b`, with the global file in
`fixtures/global-phase3.md`. Agents ran in omp 18.22. The pre-registrations
are `evals/ablation/prereg/phase3-<family>.md`. Changes made after them are in
`phase3-amendments.md`, and the frozen dial levels are in
`phase3-dials.json`. Bands follow `stats.assign_bands`.

Each scored run used 12 sessions per variant and arm (36 per arm), with arms
interleaved in a shuffled order. Opus and Fable on the review and
change-framework families have 19 to 30 sessions per arm. An Anthropic API
usage limit stopped those runs before they finished.

## What changed

Nothing. No section was deleted or rewritten.

- **Deletions.** A deletion needs every model that really loads the skill to
  show no difference. GPT 6.1 Sol is the main real loader of every skill
  tested, and it was unavailable: a weekly ChatGPT limit, and no Bedrock
  access.
- **Rewrites.** No section was harmful, so there was nothing to rewrite.

## Decision rule

Each decision check is compared with a Mantel–Haenszel risk difference,
stratified by variant, with a margin of 20 points. One Holm correction covers
all 61 family × check × model comparisons (244 tests). The bands are:

- **insensitive:** `minus-skill` does not drop by at least the margin, so the
  test cannot judge the candidates;
- **keep:** `minus-candidates` drops by at least the margin;
- **harmful:** `minus-candidates` rises by at least the margin;
- **equivalent:** two one-sided tests put `minus-candidates` within ±20 points
  of `full`;
- **inconclusive:** none of the above.

The planned 70 sessions per arm were cut to 36 for cost (`phase3-amendments.md`).
That sample can show a keep. It cannot usually show equivalence, and no
comparison reached it.

## Families where removing the skill changed nothing

In these families the models behaved correctly without the skill, so the test
could not judge the candidate sections. That is not evidence that the text is
idle; the scenario may simply be too easy.

- **planning-lenses, removal-bookkeeping, slicing-discipline** (Opus and Fable)
  and **code-config** (Fable): `minus-skill` stayed within 17 points of `full`
  on every decision check.
- **tracker-ranking** (Opus and Sonnet): 1.00 in every arm.
- **tracker-holds** (Opus and Sonnet): `hold_intact` fell from 1.00 to 0.56
  with the skill removed on both models. That drop did not survive the
  correction across 244 tests. On Sonnet, removing only the candidates left
  0.94, so other text carries the behavior.
- **delegated-member-stops on Fable:** `no_push` fell from 1.00 to 0.68, which
  is not significant at 21 to 28 sessions per arm. On Sonnet, `no_pr` is
  inconclusive.

## Not run

Phase 3 closes on the Claude models only. The owner decided not to run GPT
6.1 Sol: the ChatGPT Plus quota allows about 50 Sol sessions per 5-hour
window and about 300 a week, so the registered Sol run would take about three
weeks, and a run large enough to support deletions about six. Bedrock refuses
the model (HTTP 403).

- **Families that count only GPT Sol.** These are the four
  investigation-framework families, test-config, docs-conventions and the
  three takeover families. They have frozen dials but no scored runs.
  takeover-live-writer falls short of its control gate on Sonnet (5/10 in v1,
  7/10 in v3) but passes it on Sol: 30 of 30 sessions passed every decision
  check.
- **Dropped with the Sol run:**
  - topping Opus and Fable up to 36 sessions per arm on the review and
    change-framework families;
  - the todo families on Fable;
  - splits, which test one candidate span at a time inside a keep group.
  All three only inform deletions, and a deletion needs Sol. The frozen dials
  stay in place, so a later run can still be pooled with these results.

No section of these skills can be deleted on this evidence.

| investigation-framework | 0/18 | 0/18 | 0/12 | 0/12 |
| code | 0/18 | 0/18 | 0/12 | 0/12 |

Near-miss prompts loaded any skill in 2 of 108 sessions. Sonnet seldom loads a
skill it is not asked for by name. It almost never loads change-framework,
investigation-framework or code, whose rules are among those that matter most
above. On Sonnet those rules work only when something else puts the text in
context. The scored runs above inject the skill, so they measure what the
text does once loaded, not whether it loads.

## Limits

- Dials were set on Sonnet and applied to Opus and Fable, so a family can be
  too easy or too hard on another model.
- With 36 sessions per arm and one correction over 244 tests, drops between
  about 20 and 45 points can fail to reach significance (tracker-holds).
- Scenarios are small repositories built for the test.
- One confound is equal across arms: the tracker server's hold error message
  suggests the wrong recovery action.
- All scored results record the hash of their whole scenario definition, so a
  later scenario change voids them. Before that hash existed, a change to a
  scenario's setup alone was not detected. Only discarded control and pilot
  runs fall in that period, and their reruns were used.
- The Fable todo-family sessions stopped at 43 of 648 and are left out of the
  bands.
- Evaluation sessions read the user's own omp configuration, with only the
  harness overlay on top. The Sol control sessions ran after a user
  `PERSONALITY.md` was added, which changes reply style only. A user setting
  that changes tool behaviour (for example `bash.gitGuard`, which blocks
  branch creation in a main checkout) would change results, so the user
  configuration must stay fixed while evaluations run.

## Reproduce

```sh
uv run --no-project python evals/ablation/run.py run --out <dir> --scenario <id> --arm full --arm minus-skill --arm minus-candidates --reps 12 --model <model> --ceiling <usd> --ledger <file>
uv run --no-project python evals/ablation/phase3_bands.py <dir> [<dir> ...]
```

Scenario ids are `p3-<family>--v<k>--<dial>`, at the dial `phase3-dials.json`
gives for the variant. Session transcripts and results are private and not
committed.
